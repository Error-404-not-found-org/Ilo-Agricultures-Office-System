ILO AGRICULTURE OFFICE SYSTEM
COMPLETE UI DESIGN SYSTEM SPECIFICATION
Farmer Mobile, Technician Mobile, Technician Web, and Admin Web

Document purpose
This file is the single visual reference for redesigning and reviewing the system.
It defines what the product should look and feel like without changing routes,
data models, form payloads, permissions, or workflow rules.

======================================================================
1. DESIGN DIRECTION
======================================================================

Product character:
- Simple, trustworthy, calm, practical, and suitable for public service.
- Easy to understand for farmers with different levels of digital experience.
- Fast and information-focused for technicians working in the field.
- Organized and moderately dense for municipal administrators.

Design mode:
- Targeted evolution of the current design, not a complete rebuild.
- Preserve the forest-green identity and Outfit font.
- Remove decorative content that competes with records and actions.
- Keep Moowie as an optional assistant feature, not a banner on every page.

Design dials:
- Design variance: 3/10. Predictable and consistent layouts.
- Motion intensity: 2/10. Mostly static with clear interaction feedback.
- Visual density: 5/10. Comfortable but efficient for daily work.

Core principle:
The farmer should always understand what to do next. The technician should
always be able to find a farmer, animal, request, or record quickly. The admin
should always understand the municipality-wide state of the system.

2. CURRENT DESIGN TOOLS AND TECHNOLOGY
======================================================================

Mobile:
- Expo SDK 54
- React Native 0.81
- Expo Router
- NativeWind 4 with Tailwind CSS 3
- React Native StyleSheet and inline styles where already used
- Lucide React Native and Expo vector icons
- React Native Reanimated for necessary transitions only
- TanStack Query for loading, error, empty, refresh, and cached-data states
- Safe Area Context for headers and bottom navigation

Web:
- React 19
- Vite 8
- Tailwind CSS 4
- DaisyUI 5 using emerald and night themes
- Lucide React icons
- Framer Motion is installed, but should only be used for meaningful feedback
- TanStack Query for server-state screens
- Recharts, Chart.js, Leaflet, and MapLibre for data and mapping views

Recommended design workflow:
- Figma for final page mockups, component variants, and presentation review.
- Google Stitch may be used to explore a visual direction, but generated output
  must be adjusted to this specification before implementation.
- Expo Go or a development build for rapid mobile visual checks.
- Browser responsive mode for web widths and Expo Web for quick mobile previews.
- Do not introduce another component library during presentation preparation.

  Use as the dark-mode primary accent and positive status color.

Light neutral palette:
- App background:     #F8FAFC
- Main card:          #FFFFFF
- Soft input surface: #F1F5F9
- Standard border:    #E2E8F0
- Soft border:        #F1F5F9
- Primary text:       #1E293B
- Secondary text:     #64748B
- Muted text:         #94A3B8

Dark neutral palette:
- App background:     #090D16
- Main card:          #111827
- Raised/secondary:   #0F172A
- Standard border:    #1F2937
- Primary text:       #F8FAFC
- Secondary text:     #CBD5E1
- Muted text:         #6B7280

Semantic colors:
- Success/complete:   #10B981 light, #34D399 dark
- Warning/pending:    #F59E0B light, #FBBF24 dark
- Error/critical:     #EF4444 light, #F87171 dark
- Information/AI:     #2563EB light, #60A5FA dark
- Pregnancy:          amber family
- Calving/newborn:    teal family
- Health/medical:     rose family
- Inactive/cancelled: slate family

Color rules:
- Green is the brand accent, not a background for every section.
- Use red only for errors, destructive actions, emergencies, and critical urgency.
- Use amber only for pending, attention, overdue, and warning states.
- Never rely on color alone. Add a label or icon for every status.
- Avoid random purple, blue, and gradient accents unless they have domain meaning.
- Body text and controls must meet WCAG AA contrast.
- Do not place light gray text on white or dark gray text on black.

======================================================================
4. TYPOGRAPHY
======================================================================

Font family:
- Use Outfit everywhere on mobile and web.
- Do not mix Outfit with another display or body font.
- Mobile font files are loaded through @expo-google-fonts/outfit.
- Web currently imports Outfit and uses it as the default sans-serif font.

Font weights:
- Regular 400: body text and long descriptions
- Medium 500: secondary text and helper text
- Semibold 600: inputs, list metadata, and compact controls
- Bold 700: buttons, field labels, and navigation labels
- ExtraBold 800: card titles and section titles
- Black 900: page titles and major numbers only

Mobile type scale:
- Page title: 22-24 px, ExtraBold or Black
- Section title: 17-19 px, ExtraBold
- Card title: 15-17 px, Bold or ExtraBold
- Body: 14-16 px, Regular or Medium
- Input value: 15-16 px, Medium or Semibold
- Field label: 12-13 px, Bold
- Helper/status: 11-13 px, Medium
- Minimum readable text: 11 px. Avoid 8-10 px text for important information.

Web type scale:
- Page title: 24-30 px, Black
- Section title: 18-22 px, ExtraBold
- Card title: 14-17 px, Bold or ExtraBold
- Body: 13-15 px, Regular or Medium
- Table body: 12-14 px, Medium or Semibold
- Field label: 12-13 px, Bold
- Helper/status: 11-12 px, Medium

Typography rules:
- Use sentence case for page titles, buttons, fields, and navigation.
- Avoid uppercase paragraphs and long uppercase button labels.
- Uppercase may be used for very short table headings or compact metadata.
- Let translated labels wrap to two lines when necessary.
- Never truncate a form label or primary action.
- Use tabular or aligned numbers for metrics where supported.

======================================================================
5. SPACING SYSTEM
======================================================================

Use a 4-point base scale:
- 4 px: icon/text micro gap
- 8 px: related content gap
- 12 px: compact control gap
- 16 px: standard card padding and field spacing
- 20 px: mobile horizontal page padding
- 24 px: large card padding and desktop section gap
- 32 px: major section separation
- 40-48 px: rare page-level separation only

Mobile spacing rules:
- Horizontal screen padding: 16 px on very small screens, normally 20 px.
- Header horizontal padding: 20 px.
- Card padding: 16 px. Use 20 px only for important summary cards.
- Form field gap: 16 px.
- Label-to-input gap: 8 px.
- Section gap: 24-32 px.
- Bottom content padding: navigation height plus safe area plus 16 px.

Web spacing rules:
- Page padding: 16 px below 768 px, 24 px from 768 px upward.
- Main content maximum width: approximately 1400 px when practical.
- Panel padding: 20-24 px.
- Dashboard grid gap: 16-20 px.
- Table cell padding: 12-16 px.
- Modal padding: 20 px mobile web, 24 px desktop.

Do not use spacing to compensate for an oversized decorative banner. Avoid large
negative overlaps unless the overlap communicates real hierarchy.

======================================================================
6. SHAPE, BORDER, AND SHADOW SYSTEM
======================================================================

Recommended radius rules:
- Inputs, buttons, and compact controls: 12 px
- Cards and panels: 16 px
- Important mobile summary cards: up to 20 px
- Modal and bottom sheet: 20-24 px
- Avatars and icon-only circular actions: full circle
- Pills only for short filters and status badges

Border rules:
- Standard border is 1 px.
- Use the light or dark standard border token.
- Focused fields use the primary green border and a subtle focus ring.
- Error fields use the semantic error border and inline error message.

Shadow rules:
- Use shadows sparingly and only to communicate elevation.
- Light cards: very soft shadow, roughly 3-5 percent opacity.
- Dark mode: prefer borders over gray shadows.
- Lists and tables should normally use borders or spacing, not a shadow per row.

======================================================================
7. SHARED COMPONENT STANDARDS
======================================================================

Page header:
- Use the same safe-area treatment, green, title size, radius, and vertical
  padding across screens with the same hierarchy.
- Standard mobile functional header should remain compact.
- Header contains: back button when needed, title, optional short subtitle, and
  at most one primary page action.
- Decorative banners do not belong inside functional headers.
- Dashboard greeting may be richer than a list header, but must still use the
  same green and spacing family.

Buttons:
- Primary: solid Forest Green, white label, 44-48 px mobile height.
- Secondary: white/card surface, standard border, primary or dark text.
- Destructive: red only when the action is actually destructive.
- Icon-only target: minimum 44 x 44 px mobile, 36 x 36 px web.
- Buttons show disabled and loading states without changing their width.
- Button labels should be one clear verb phrase: Register farmer, Add record,
  Save changes, Accept request, or Try again.

Inputs:
- Label above the control.
- Optional helper text below the label or control.
- Error below the control and near the problem.
- Never use placeholder text as the only label.
- Standard mobile field height: 48-52 px.
- Standard web field height: 40-44 px.
- Use one shared searchable selection pattern for Farmer and Animal fields.

Searchable farmer/animal selector:
- Closed state must look like other form fields.
- Show label, selected name, and useful secondary identifier.
- Farmer secondary line: barangay or contact number.
- Animal secondary line: ear tag, species, and owner.
- Open as a bottom sheet on mobile and dialog/popover on web.
- Include search, loading, empty, error, selected, and disabled states.
- Do not implement a different farmer modal inside each form.

Cards:
- Use cards for summaries, grouped details, and actionable records.
- Avoid placing every line in its own card.
- Card header contains one title and at most one action.
- Keep the same internal spacing and radius across roles.

Lists and tables:
- Mobile uses list cards or grouped rows with the most important identity first.
- Web uses tables for comparison-heavy data and cards only where scanning is
  improved by a card layout.
- Farmer name, animal tag, record type, date, and status should be easy to scan.
- Entire mobile list rows may be tappable. Web rows should have clear actions.

Badges:
- Status badges use semantic color, text, and border.
- Use consistent labels across mobile and web.
- Keep badges compact and never replace a clear sentence with many badges.

Modals and sheets:
- Mobile selection and quick action flows use bottom sheets when practical.
- Mobile confirmation may use a centered dialog.
- Web uses centered dialogs for forms and side drawers for long record history.
- Every modal has title, close action, scroll containment, and keyboard support
  where applicable.

Loading, empty, error, and offline states:
- Loading: skeleton shaped like the real content.
- Empty: explain what is missing and how to add or find it.
- Error: inline contextual message with one Try again action.
- Toast: reserved for a completed user action or brief transient failure.
- Never show repeated toasts for the same query failure.
- Offline status must not permanently cover action-result toasts.

======================================================================
8. FARMER MOBILE DESIGN
======================================================================

Primary experience:
- Friendly, guided, and low-stress.
- Use plain language and explain unfamiliar livestock terms.
- Show the farmer's animals, requests, records, and next actions first.

Navigation:
- Bottom tabs: Home, My Animals, Records, Profile.
- Labels must support English, Filipino, and Hiligaynon wrapping.
- Keep icons and labels aligned with a stable tab height.

Home:
- Simple greeting and farm overview.
- Show urgent or upcoming items before educational or promotional content.
- Limit quick actions to the most common actions.
- Moowie may appear as one optional assistant entry, not repeated banners.

My Animals:
- Search and filters at the top.
- Each animal card prioritizes photo, name/tag, species, sex, and status.
- Animal details show identity, reproductive state, requests, and history.

Records:
- Prioritize official service history and understandable status labels.
- Recent activity filter should use a dropdown or sheet, not crowded chips.
- Remove persistent Moowie analysis banners from the records workflow.
- Make record detail dates and technician/service information explicit.

Requests and support tickets:
- Farmer must see every submitted request or ticket.
- Show Pending, Accepted/Scheduled, Completed/Resolved, Rejected, or Cancelled.
- Each item must explain the current state and expected next action.

Forms:
- One clear task per screen.
- Group fields into short, named sections.
- Required fields are visible before submission.
- Critical health urgency maps to the supported emergency value.
- Submission feedback must distinguish saved online, queued offline, and failed.

======================================================================
9. TECHNICIAN MOBILE DESIGN
======================================================================

Primary experience:
- Fast field workflow focused on farmers, animals, requests, and records.
- Reduce decoration and keep functional content near the top.
- Technician must reach a specific animal's complete history with few taps.

Navigation and information architecture:
- Dashboard: today's work and urgent requests.
- Farmers: farmer directory and farmer profiles.
- Animals: animal registry and animal profiles.
- Records: official cross-farmer record search and reports.
- Profile: account, support, and sync tools.

Headers:
- Standardize green background, safe-area padding, title position, back button,
  radius, and action placement.
- List pages at the same hierarchy use the same header height.
- Forms use one compact header style.
- Remove Moowie banners from Farmers, Animals, Records, and record forms.
- Keep Ask Moowie as an optional destination if retained.

Dashboard:
- Top priorities: today visits, pending requests, urgent cases, quick actions.
- Avoid large greeting banners that push work below the fold.
- Metrics must link to the related list when useful.

Farmers:
- Search by name, contact, or barangay.
- Farmer profile shows contact, location, animal count, requests, and records.
- Primary actions: View animals, Add animal, Add record, Contact farmer.

Animals:
- Search by ear tag, name, owner, species, or breed.
- Animal profile keeps an identity/context header visible.
- Show complete chronological history in one understandable timeline.
- Add current record and Add past record must be clearly distinguished.

Records and record forms:
- Use one standard Farmer selector and one standard Animal selector.
- After choosing a farmer, show only that farmer's animals.
- Do not duplicate farmer-selection modal styles across forms.
- Clearly identify official request-derived records versus manual past records.
- Service date and entry date must both be visible when different.

Requests:
- Separate Pending, Assigned/Scheduled, and Completed when necessary.
- Actions must reflect the canonical backend workflow.
- Avoid technical endpoint terminology in visible labels.

Offline and sync presentation:
- Show a compact offline indicator, not a permanent blocking toast.
- Queued submissions return the UI to a stable state immediately.
- Sync Center should be reachable from technician profile/support.
- Show queue count, last sync, per-item state, retry, and understandable errors.

10. TECHNICIAN WEB DESIGN
======================================================================

Primary experience:
- Desktop command center for finding farmer and animal records quickly.
- Same terminology and status meanings as technician mobile.

Sidebar naming:
- Dashboard
- Farmers
- Animals
- Requests
- Records
- Tasks or Schedule, only if both are genuinely separate workflows
- Reports, only if it is not already inside Records
- Support
- Profile/Settings

Avoid duplicate or vague names such as Clients versus Farmers, Record Service
versus Records, or multiple request destinations with unclear ownership.

Core demonstration path:
- Dashboard
- Farmers directory
- Farmer profile
- Animal profile
- Complete history
- Add current or past record
- Confirm the farmer mobile app displays the same official record

Layout:
- Persistent desktop sidebar.
- Collapsible or drawer navigation below approximately 1024 px.
- Page header above content with title, short context, and one primary action.
- Search and filters remain near the list they control.
- Tables become stacked record cards below approximately 768 px when horizontal
  comparison is no longer usable.

======================================================================
11. ADMIN WEB DESIGN
======================================================================

Primary experience:
- Municipal overview, governance, monitoring, and exception handling.
- More data-dense than mobile but still calm and readable.

Core admin pages:
- Dashboard
- Users
- Animals
- Records
- Request Monitoring
- Support Tickets
- Barangay Insights
- Technician Workload/Performance
- Audit Logs
- Settings

Dashboard hierarchy:
- First row: municipality totals and urgent exceptions.
- Second section: request and service trends.
- Third section: barangay or technician comparison.
- Final section: recent activity and links to detailed monitoring.
- Avoid decorative AI summary cards unless they provide actionable information.

Tables:
- Sticky or clearly separated headers for long tables.
- Search, filter, and export actions grouped in one toolbar.
- Use pagination for large server datasets.
- Use consistent row actions and confirmation patterns.
- Keep column count limited. Move secondary data to details view.

Admin actions:
- Destructive and permission-changing actions require confirmation.
- Show who/what is affected before confirmation.
- Audit events should use plain language and retain exact timestamps.

======================================================================
12. RESPONSIVENESS
======================================================================

Mobile app targets:
- Narrow phone: approximately 320-359 dp
- Standard phone: approximately 360-419 dp
- Large phone: approximately 420-599 dp
- Tablet: 600 dp and wider

Mobile rules:
- Never hard-code a width that assumes one phone size.
- Use safe areas for top headers, bottom navigation, sheets, and keyboards.
- Use flexWrap for translated control groups.
- Stack side-by-side form fields on narrow phones.
- Keep touch targets at least 44 x 44 dp.
- Support font scaling without clipping primary actions.
- Lists should use the available width, not fixed pixel card widths.
- On tablets, constrain long forms rather than stretching fields edge to edge.

Web breakpoints:
- Small: below 640 px
- Medium: 640-767 px
- Large/tablet: 768-1023 px
- Desktop: 1024-1279 px
- Wide desktop: 1280 px and above

Web rules:
- Mobile first, then enhance with columns and persistent navigation.
- One-column forms on small widths; two columns only for closely related fields.
- Dashboard grids: 1 column small, 2 medium, up to 3 or 4 wide desktop.
- Dialog width must never exceed the viewport; long content scrolls internally.
- Navigation labels stay on one line at desktop.
- Avoid horizontal page scrolling. Allow table-specific scrolling only as a
  temporary fallback before implementing a responsive card view.

======================================================================
13. ACCESSIBILITY AND LANGUAGE
======================================================================

- Minimum touch target: 44 x 44 dp mobile.
- Visible keyboard focus on every interactive web element.
- Every icon-only button has an accessible label or tooltip.
- Every form input has a persistent label.
- Error messages explain how to fix the problem.
- Status is communicated with text and not color alone.
- Respect reduced-motion preferences.
- Test English, Filipino, and Hiligaynon on narrow and standard phones.
- Allow two lines for navigation and action labels where needed.
- Do not shrink essential text below readable size just to fit a translation.
- Screen-reader reading order must follow the visual workflow.

======================================================================
14. MOTION AND FEEDBACK
======================================================================

- Motion must explain feedback or state change, not decorate the interface.
- Use quick press feedback, sheet/dialog transitions, and skeleton shimmer only.
- Recommended duration: 150-220 ms for controls, 220-300 ms for modal/sheet.
- Animate opacity and transforms rather than layout dimensions.
- Avoid infinite pulses, floating characters, and repeated auto-animations.
- Haptics may confirm important mobile actions but should not fire for every tap.

======================================================================
15. CONTENT AND NAMING RULES
======================================================================

Use these terms consistently:
- Farmer, not Client, in user-facing technician interfaces.
- Animal Registry for the searchable animal collection.
- Records for official service and animal history records.
- Requests for submitted service requests.
- Artificial Insemination may be shortened to AI only after the full term is
  established in the screen context.
- Pregnancy Diagnosis, not multiple competing pregnancy-check labels.
- Health Assistance for technician service records.
- Report Health Issue for the farmer request action.
- Add Past Record for an already completed historical service.

Button naming examples:
- Register farmer
- Register animal
- Add record
- Add past record
- Submit request
- Accept request
- Schedule visit
- Mark complete
- Save changes
- Try again

Avoid vague labels such as Continue, Process, Manage, Service, or Submit when a
more specific verb is available.

======================================================================
16. DESIGN QA CHECKLIST
======================================================================

Before accepting any redesigned screen, verify:

[ ] It uses Outfit and the approved font scale.
[ ] It uses the shared green and neutral palette.
[ ] Header height matches screens at the same hierarchy.
[ ] Spacing follows the 4-point scale.
[ ] Inputs, buttons, cards, and modals use the shared radius rules.
[ ] Primary action is obvious and not duplicated.
[ ] Farmer and animal selectors match the standard pattern.
[ ] Loading, empty, error, disabled, and success states exist.
[ ] Query failures do not create repeated toast messages.
[ ] Light and dark modes remain readable.
[ ] English, Filipino, and Hiligaynon labels fit.
[ ] Narrow phone, standard phone, tablet, and desktop layouts were checked.
[ ] Keyboard and safe-area behavior were checked on mobile.
[ ] Keyboard focus and modal focus behavior were checked on web.
[ ] No decorative banner pushes the main task below the fold.
[ ] The screen uses the same terminology as mobile, web, and backend status.
[ ] The complete farmer-to-animal-to-history workflow remains understandable.

17. IMPLEMENTATION ORDER
======================================================================

Design first:
1. Create Figma foundations: colors, type, spacing, radius, buttons, fields.
2. Create one mobile header, one mobile list card, and one mobile form pattern.
3. Create one web page header, panel, toolbar, table, and dialog pattern.
4. Mock the technician farmer-to-animal-to-history workflow.
5. Mock the farmer records and request-status workflow.
6. Mock the admin dashboard and one representative admin table.

Implement after visual approval:
1. Shared mobile foundations.
2. Technician mobile high-use screens.
3. Farmer mobile high-use screens.
4. Shared web foundations.
5. Technician web workflow.
6. Admin web dashboard and management pages.
7. Responsive and language pass.
8. Loading, empty, error, offline, and accessibility pass.

Do not redesign every page independently. Approve the shared foundations and
representative workflows first, then apply them systematically.
